## 1. Authentication vs. Authorization

Understanding the distinction between Authentication and Authorization is a core pillar of application security:

| Concept | Definition | ExpenseTrack Implementation |
| :--- | :--- | :--- |
| **Authentication (AuthN)** | Verifying **who** the user is (validating credentials). | `routes/auth.py` validates email/username and compares password hash via `check_password_hash()`. On success, issues signed session cookie. |
| **Authorization (AuthZ)** | Verifying **what** permissions the authenticated user possesses (access control). | `routes/auth_helper.py` (`@login_required`) and database query filters (`WHERE user_id = %s`) ensure students can only view or mutate their own transactions. |

## 2. Cryptographic Password Hashing: Scrypt KDF

ExpenseTrack deliberately avoids legacy or weak algorithms (MD5, SHA-1, plain SHA-256) and employs **Scrypt**, a modern memory-hard Key Derivation Function (KDF):

```
Plaintext Password: "Password123!"
        +
Cryptographic Random Salt: (16 bytes random per user)
        |
        v
[ Scrypt KDF: N=16384 (CPU/Memory Cost), r=8 (Block Size), p=1 (Parallelism) ]
        |
        v
Stored Hash: "scrypt:32768:8:1$u7xK...$9b1e..."
```

### 2.1 Why Scrypt over Standard SHA-256?
- **Speed is a Vulnerability in Password Hashing:** Standard cryptographic hashes (SHA-256, SHA-512) are engineered to be extremely fast for data integrity checks. However, specialized GPUs or ASIC rigs can compute billions of SHA-256 guesses per second, enabling rapid offline brute-force and dictionary attacks.
- **Memory Hardness:** Scrypt requires a substantial amount of working RAM for each evaluation. This memory footprint dramatically degrades the performance of massively parallelized GPU and ASIC cracking rigs.
- **Unique Cryptographic Salt:** Every password hash generated by Werkzeug contains a cryptographically random salt. Even if two students choose the identical password (`Password123!`), their stored hashes are completely distinct, rendering precomputed **Rainbow Table attacks** useless.

## 3. Session Management & Cookie Security Architecture

Client sessions are managed via Flask's cryptographically signed cookie mechanism with enterprise-grade flags configured in `config.py`:

```python
SESSION_COOKIE_HTTPONLY = True      # Mitigates Cross-Site Scripting (XSS)
SESSION_COOKIE_SAMESITE = "Lax"     # Mitigates Cross-Site Request Forgery (CSRF)
SESSION_COOKIE_SECURE = False       # Set to True on production HTTPS environments
PERMANENT_SESSION_LIFETIME = 86400  # Enforces 24-hour expiration window
```

### 3.1 Defense Mechanics
1. **HttpOnly Flag:** Prevents client-side JavaScript (`document.cookie`) from reading the session cookie. Even if an attacker executes an XSS payload via a reflected script, they cannot steal the student's session token.
2. **SameSite=Lax Flag:** Restricts the browser from sending the session cookie on cross-site requests (e.g., when a user is tricked into clicking an external phishing link), blocking Cross-Site Request Forgery (CSRF).
3. **Session Invalidation on Logout:** Calling `session.clear()` immediately purges server-stored user context, preventing session reuse.

## 4. Multi-Tenant Data Isolation & IDOR / BOLA Prevention

**Broken Object-Level Authorization (BOLA)**—also referred to as **Insecure Direct Object Reference (IDOR)**—is the #1 vulnerability on the OWASP API Security Top 10.

### 4.1 The Threat Scenario
Student A (user_id = 1) logs into ExpenseTrack. Student B (user_id = 2) owns expense record `#45`. Student A attempts to manipulate the request:
```http
POST /api/expenses/delete/45 HTTP/1.1
Host: 127.0.0.1:5000
Cookie: session=... (Student A's valid session)
```

### 4.2 How ExpenseTrack Mitigates BOLA
ExpenseTrack never relies solely on the path parameter `id`. The backend query strictly binds the tenant identifier from the validated session:
```sql
DELETE FROM expenses 
WHERE id = %s AND user_id = %s;
```
If expense `#45` belongs to Student B (`user_id = 2`), the query matches 0 rows. The controller detects `rowcount == 0` and returns a `404 Not Found` or `403 Forbidden`, guaranteeing absolute multi-user isolation.

## 5. Defense-in-Depth against SQL Injection

SQL Injection occurs when untrusted user input alters the syntactic structure of an SQL query.

### 5.1 Parameterized Queries via PyMySQL Driver
ExpenseTrack never concatenates variables into SQL strings. All database queries utilize parameterized statements:
```python
# SECURE: Data is sent separately from the SQL command structure
cursor.execute(
    """
    SELECT id, amount, merchant, expense_date 
    FROM expenses 
    WHERE user_id = %s AND category_id = %s;
    """,
    (current_user_id, selected_category_id)
)
```
1. The database parser compiles the SQL query template.
2. The parameters are transmitted via the DB-API protocol and treated strictly as literal data constants.
3. Any SQL metacharacters (such as `'`, `;`, `--`) contained within the input are safely escaped and cannot manipulate query execution.

## 6. Secure File Upload Pipeline

Receipt uploads present attack surfaces including arbitrary code execution, path traversal, and Denial of Service (DoS). ExpenseTrack enforces a multi-tier defense:

```
[ Uploaded File ]
       |
       v
1. Content-Length Check (Enforces MAX_CONTENT_LENGTH = 5MB to prevent DoS)
       |
       v
2. Extension Whitelist Check (.png, .jpg, .jpeg, .webp ONLY - rejects .exe, .php, .py)
       |
       v
3. Filename Sanitization (werkzeug.utils.secure_filename strips "../" path traversal)
       |
       v
4. UUID4 Cryptographic Renaming (e.g., "7a8b9c...f4.png" - prevents file overwrite & predictable URLs)
       |
       v
5. SHA-256 Digest Computation (Flags duplicate receipts without double-processing)
       |
       v
6. Isolated Storage (Saved in private uploads directory or Azure Blob container)
```

## 7. Encryption: In Transit and At Rest

| State | Threat Vector | Mitigation Strategy |
| :--- | :--- | :--- |
| **In Transit** | Man-in-the-Middle (MitM) eavesdropping, packet sniffing on campus Wi-Fi. | Enforce **TLS 1.3 / HTTPS** encryption. Set `SESSION_COOKIE_SECURE = True` and configure HTTP Strict Transport Security (`HSTS`). |
| **At Rest** | Stolen hard drives, unauthorized database file access. | **Transparent Data Encryption (TDE)** at the database engine level (AES-256). Operating system full-disk encryption (BitLocker / LUKS). Azure Blob Storage server-side encryption (256-bit AES). |

## 9. Cloud Security Viva Q&A (10 Questions)

**Q1: Why is Scrypt superior to MD5 or SHA-1 for storing passwords?**  
*Answer:* MD5 and SHA-1 are cryptographically broken, extremely fast general-purpose hashes with zero memory hardness. Attackers can compute billions of SHA-1 hashes per second using GPUs. Scrypt is a memory-hard key derivation function that requires significant RAM per computation, rendering GPU and ASIC brute-force attacks economically and computationally infeasible.

**Q2: What is the purpose of adding a salt to a password before hashing?**  
*Answer:* A salt is a cryptographically random string appended to the password before hashing. It ensures that identical passwords yield completely different hashes, thwarting precomputed dictionary attacks and rainbow tables.

**Q3: How does the `HttpOnly` flag on a cookie prevent session hijacking?**  
*Answer:* The `HttpOnly` directive instructs the browser that the cookie must not be accessible via client-side scripts (e.g., `document.cookie`). If an attacker injects a malicious XSS script, the browser blocks the script from reading or exfiltrating the session cookie.

**Q4: What is Broken Object-Level Authorization (BOLA/IDOR) and how do we prevent it?**  
*Answer:* BOLA occurs when an endpoint accepts a resource ID from user input without verifying that the requesting user owns that resource. ExpenseTrack prevents this by binding all SQL mutations and queries to the session user ID (`WHERE id = %s AND user_id = %s`).

**Q5: What is the difference between encryption and hashing?**  
*Answer:* Hashing is a **one-way** mathematical transformation that converts data into a fixed-length digest; it cannot be reversed. Encryption is a **two-way** process that transforms plaintext into ciphertext using a key, which can be decrypted back to plaintext with the matching key.

**Q6: What is the Principle of Least Privilege (PoLP)?**  
*Answer:* PoLP dictates that every module, user, or process must possess only the minimum privileges necessary to perform its intended function. In production, the Flask application connects to MySQL via an unprivileged database user granted only `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on `expensetrack`, with no `DROP DATABASE` or `GRANT` privileges.

**Q7: How do you prevent Path Traversal attacks during file uploads?**  
*Answer:* If an attacker uploads a file named `../../etc/passwd` or `..\windows\system32\cmd.exe`, using that name directly can overwrite system files. We use `werkzeug.utils.secure_filename` to strip relative path characters, and replace the filename entirely with a random UUID4 string (`uuid.uuid4().hex`).

**Q8: What is CSRF (Cross-Site Request Forgery) and how does `SameSite=Lax` protect against it?**  
*Answer:* CSRF tricks a victim's browser into executing unwanted actions on an authenticated web app. With `SameSite=Lax`, modern browsers refuse to send the session cookie on cross-site requests initiated by third-party origins (such as unauthorized POST submissions from malicious sites).

**Q9: Why should financial web applications never store UPI PINs or OTPs?**  
*Answer:* UPI PINs and OTPs are sensitive two-factor authentication credentials governed by strict regulatory standards (such as RBI and PCI-DSS). A financial tracker only requires record of *completed* transactions (amount, merchant, date); storing banking credentials creates severe legal liability and catastrophic security exposure.

**Q10: What is the difference between Symmetric and Asymmetric encryption?**  
*Answer:* Symmetric encryption uses the same secret key for both encryption and decryption (e.g., AES-256, used for data at rest). Asymmetric encryption uses a mathematically linked key pair: a public key for encryption and a private key for decryption (e.g., RSA/ECC, used in TLS handshakes for data in transit).
